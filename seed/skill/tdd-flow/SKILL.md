# tdd-flow

> 把大功能从"想法"安全送到"已验证落地"。核心是测试先行：先写测试描述"做对"长什么样，再写实现让它过。只在明确需要这套纪律时启用，不套到日常小改上。

## 何时用

- 用户明确要求 TDD / 测试先行，或主动选择本工作流。
- 核心逻辑、边界多、易回归，值得先写测试再实现。

"认真做""严格点"表达的是质量期待，具体投入按任务决定，不自动触发本流程。

## 红线

- 永不 push；按影响面验证；未经用户明确要求不 commit。

## 流程

1. 测试先行：先写测试描述预期行为，再写实现让它过。
2. 实现只写够让测试过的量，不顺手做下个任务。
3. 简单逻辑或测试成本明显大于收益时，直接实现并补关键测试；核心逻辑、边界多、易回归的地方坚持先行。
4. 收尾：按影响面验证（受影响 package 的 typecheck + 对应测试全绿），仓库级改动才跑全量（TUI→packages/redspace，GUI→packages/desktop）。

## Anti-patterns

- 假 TDD：先写实现再补测试，或测试从没真红过。
- 拿这套流程做一行修复，为走流程烧 token。

## 关系

- `goal-automation` 跑长流程前先 /goal 钉目标防跑偏。
- `diagnose` 发现 bug 时的调试纪律。
- `simplify` 发现过度工程时的精简纪律。
