# 执行历史分两本账：旧步骤与新请求

状态:implemented

## 问题

同一模型相邻三次请求曾出现 `96.67% → 17.22% → 96.73%` 的缓存命中率，没有换模或压缩。旧记录能证明低点存在，却不能说明哪段输入变了（[当时的证据](2026-10-04-compression-request-evidence.md#长请求诊断补充)）。每个会话的最新 Context 快照即使还在磁盘上，也不是这个低点的快照。

## 决策

- **步骤**读当前分支已有的 `step-finish`。一个回复可记多步；失败重试有可能没留下步骤。单步用自己的 token、费用、币种与估算标记，不借助手消息的累计值。总输入取 `tokens.context`；它缺失时不拿缓存数反推。账面缓存是经过归一化的数字，账面零不证明供应商显式报零。
- **请求**从升级后的本地执行开始记。有明确助手消息归属的模型调用尝试才写 `flight_request`；摘要请求也归自己的消息。观察点是 SDK 模型调用或原生传输，不是网络抓包，不能用行数反推内部鉴权、代理转发或 TCP 重连次数。尝试 ID 用现有 RequestEvidence 的关联号；前缀只取同会话、模型及运行时观察器算出的系统、工具、历史三段变化。不再序列化一遍正文，不从日志回填。基线没有可比前任；“观察到新压缩”与“历史改写”不是同一证据，二者都不能单独解释缓存失效。
- 两端展开时才读，未展开不轮询。`GET /session/:sessionID/flight-recorder` 每页默认 20、最多 50 行；游标绑定来源和会话，用 `(time_created, id)` 排序，同毫秒不漏行。只查当前分支的标识与统计，不拉整条消息或分片正文。已加载记录的汇总不代表会话总量；缺失、估算、零分母、读缓存超过总输入等情况不能冒充实报命中率。
- 新表每会话最多 128 次，随消息或会话删除。最终状态只能更新仍在的尝试，不能复活已淘汰的行。只记标识、状态、数值和几种变化分类；不记正文、账号、请求头、响应正文、路径或错误文本。采集失败不等于模型失败。

## 取舍

不把两种记录拼成一个计数：续写和重试让步骤与请求不能一一对应。没有实测的工具耗时、首字时间或服务端缓存原因就不画；“首事件”不是“首字”。没有单独服务、定时扫库或按流分片写盘。本功能不修改模型输入、工具描述、固定前缀或缓存键；新增模型上下文为 0 token。

旧步骤的部分索引以一次升级时扫描 `part` 换取查询不必全场排序。隔离 SQLite 样本（1,500 条消息、6,000 个分片、翻 21 行）中，`EXPLAIN QUERY PLAN` 从临时 B 树变为复合索引范围扫描；11 次热查的中位数从 3.067 ms 到 0.032 ms。这是合成读侧样本，不是现有用户库的迁移耗时或整端性能数据。

## FR-02 缓存诊断

请求详情保存同一会话、模型、运行时桶中上一次成功采集的请求 ID。观察失败保留原因且跳过基准更新。GUI 和 TUI 只用该 ID 对应的已加载请求显示基准命中率。`wire` 比较系统、历史和工具组成的有序序列，`serialized` 比较整份请求 JSON。压缩以本地标记推进或观察到的回执为证据，回执的 Token 数为估算值。

新增 `diagnostics` 版本为 1，旧行可继续读取。每行诊断是三个固定分段、一次基准关联、有限枚举、至多一组聚合压缩统计和一组供应商归因。每会话仍保留 128 条，压缩只聚合观察器已保有的至多 128 份待消费回执。同桶最多多保留一个请求 ID 与六个匿名亲和指纹，写入诊断仅取变化分类和数值。

模型输入、固定前缀、缓存键与出站顺序沿用既有路径。固定前缀增量为 **0 字节、0 Token**。供应商报出的 Instructions 读写保留显式零。本次请求总量和 Instructions 归因数据一致时，才从总未读缓存中扣减指令未读量。DeepSeek 的 miss 记为未读缓存，Anthropic 的总输入在三个组成项齐全时计算。

## FR-03 写入与计时

出站和结算回调只更新进程内队列。队列最多保留 256 个待写请求，每批最多处理 32 个。请求完成时若起始行还在队列里，两次写入合为一条；已写入的请求使用按 ID 的批量更新。一个事务查询尚存的父消息、写入合并后的新行、按 `(time_created, id)` 批量裁剪受影响的会话。这样消息已删除的请求不会拖累同批记录，迟到结算也不会重新插入已删除或已裁剪的行。

飞行记录仪批次以零等待取得写锁，结束后恢复会话数据库的 `busy_timeout`。遇到写锁每隔 20 ms 再试，至多等待约 250 ms。超过窗口时丢弃积压，写入错误丢当前批，队列已满时丢新待写项，已有的同 ID 结算仍可以合并。丢弃按待写项计数，首次及之后每分钟至多告警一次。正常退出时最多尝试写一批，剩余记录丢弃。强制结束进程会丢失尚未落库的记录。

墙钟只用于请求记录的创建时间。持续时间和首事件延迟使用单调时钟。首事件的观察点是适配后的流，可包含 SDK 的 `step-start`，读数受流消费调度影响。已观察到供应商 finish 时，耗时截止到 finish，本地后续工具等待不计入。模型输入及固定前缀增量为 0，缓存键沿用原有路径。

在 `packages/redspace` 下运行 `bun run --conditions=browser ./script/bench-flight-recording.ts`。脚本为每次运行创建独立的临时数据库。启停两组共用同一模拟供应商，包含单会话、带 8,192 条历史记录的 16 会话并发、模拟 503 与续写、独立进程持写锁，以及 SQLite `query_only` 写入失败场景。输出为 P50/P95/P99，`hookMs` 为起始与结算回调耗时，`sampledBatchMs` 为按轮抽样的批次尝试耗时，WAL 指运行结束时的文件大小。分位数用于本地诊断，写锁样本较少，P95 和 P99 可能落在同一个样本。

## FR-04 全局观测

会话内的双账本只能看单个会话。跨会话入口是 `GET /session/flight-recorder/summary` 与 `/rows`；作用域由服务端 `InstanceState` 解析，客户端传入的 project、workspace、session、provider、model 只能收窄，不能当授权凭证。当前实现只覆盖本实例的项目（工作区受限时含该工作区），不跨服务器，也不把远端不可达当成空数据。

隔离落在索引层而不是结果过滤。`flight_scope` 按 `(kind,id)` 投影 step-finish 与请求行的 `project_id`、`workspace_id`、`visible`，触发器维护 part 的 `data` 类型双向变化、消息 detached 切换、会话迁移和级联删除，迁移对旧库做一次回填。全局窗口只从该表取当前作用域的行：其他项目的行不进入 `LIMIT`，也不进入 cursor、coverage 或 `scanned`。2026-11-26 之前的实现先扫全库再过滤，游标与计数会泄漏范围外的 ID、时间和活跃量，因此废弃。

每页扫描预算 1000 行、summary 每账本 5000 行，`MATERIALIZED` 窗口阻止过滤下推让预算失效。窗口没有命中但仍有更旧行时返回 `next` 并标记 `truncated`；继续跟随游标才能判定历史，空页不等于不存在。summary 的续查游标按账本分开，只扫描游标里带的账本。窗口结果按构造就是局部的：可加字段跨窗口累加，会话去重数和延迟分位数是窗口局部值，provider/model 分组受 `MAX_GROUPS` 截断。

双账本不合并；费用只从步骤账按币种聚合，缺失不补零、不换汇；请求侧不复制步骤费用。保留元数据读取 FR-05 的生效策略，不再把 128 写死。步骤账投影 FR-06 的 `requestID`，旧记录缺失时保持未关联，不 JOIN 请求行猜测。

`part_flight_step_time_idx` 随本次移除：全局窗口改由 `flight_scope` 承担后它没有任何查询消费者，真实库升级却要多构建一棵约 9 秒的 partial 索引并常驻空间。`flight_request(time_created,id)` 保留，容量边界查询仍需要。

## FR-05 容量治理

请求记录现在有三项全局配置：`flight_recorder.max_requests_per_session`（默认 128）、`max_total_requests`（默认 100000）、`retention_ms`（默认不启用）。三项都是有限正整数并带实测上限（100 万条 / 10 年）：边界是 `LIMIT 1 OFFSET keep-1` 的索引扫描，成本随上限线性增长；`Schema.Int` 已拒绝 unsafe integer。

删除范围只有 `flight_request`。账单步骤、消息和会话不由此路径删除；行数上限不是 SQLite 文件字节上限，删除后空间靠空闲页复用，不执行 `VACUUM`。

启动不按默认值清理。`boot` 通过应用同一个 Config 服务读取全局配置，只有解析与校验成功才置 ready；读取失败保留未就绪状态并定期重试，绝不退回默认上限删除旧库。写入批在未就绪时只落行不裁剪。

同一 tick 内先完成全部 session/age 删除，再计算一次全局边界并连续裁剪。会话删除会让总数下降，事后复用旧边界会把最老行多删到低于上限；阶段隔离后边界只在所有改变行集的删除完成后计算。边界与删除在同一 `BEGIN IMMEDIATE` 事务内，跨进程写锁串行化；迟到结算只 `UPDATE`，已淘汰行不会复活。

清理是渐进有界的：每批最多 32 行、每 tick 最多 4 步；积压时 25 ms 推进，空闲 60 s 巡检，配置变更后无需重启即可收敛。限定配置上限的另一个依据是：全局边界扫描与每批删除都在写锁内，上限越高单步成本越高。

## FR-06 请求与账单关联

关联的语义是「该账单事件的用量确由这些模型调用产生」，不是「它们出现在同一消息或相近时间」。请求 ID 随真实响应传递：

- native：出站 ID 挂在实际返回的 `HttpClientRequest` 上，只有成功响应才登记，503 淘汰的尝试不会抢账单；transport 在解码前读取，只给该响应产出的 `step-finish` 附加 `requestID`。`HttpPrepared` 在每次订阅时重建请求实例，同一流被并发消费时关联号和响应不会互相覆盖。
- AI SDK：middleware 在每次实际 `doStream` 响应上把 headers 换成同内容独立对象并按对象身份绑定本次 ID；适配层只认 `finish-step.response.headers` 仍是这个对象时关联。SDK 克隆对象或没有 headers 时保持未关联，不按 current、FIFO 或时间猜。
- processor 把 `requestID` 与 cost/tokens 放在同一次 `updatePart` 写入；旧账单解码为未关联，不做历史回填。估算事件（断流补估、重复内容停止）不携带关联号。
- `StepFinishPart.requestID` 上限 64 字符，唯一生产者是 `crypto.randomUUID()`（36 字符）。

已关联但请求详情不在已加载集合时，UI 只能说「未在已加载请求中」，不能断言已被淘汰——也可能是入队丢弃、写失败或尚未刷盘。一个账单关联多个请求时只展示步骤总费用，请求侧不复制费用。

模型可见影响：三项功能都不改变模型请求。关联号不进入 body、header、query 或供应商字段，有出站字节对照测试；固定前缀新增 0 字节、0 token，KV cache 条件不变；容量上限只作用于本地记录表。
