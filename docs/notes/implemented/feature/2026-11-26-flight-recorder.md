# 执行历史分两本账：旧步骤与新请求

状态:implemented

## 问题

同一模型相邻三次请求曾出现 `96.67% → 17.22% → 96.73%` 的缓存命中率，没有换模或压缩。旧记录能证明低点存在，却不能说明哪段输入变了（[当时的证据](2026-10-04-compression-request-evidence.md#长请求诊断补充)）。每个会话的最新 Context 快照即使还在磁盘上，也不是这个低点的快照。

## 决策

- **步骤**读当前分支已有的 `step-finish`。一个回复可记多步；失败重试有可能没留下步骤。单步用自己的 token、费用、币种与估算标记，不借助手消息的累计值。总输入取 `tokens.context`；它缺失时不拿缓存数反推。账面缓存是经过归一化的数字，账面零不证明供应商显式报零。
- **请求**从升级后的本地执行开始记。有明确助手消息归属的模型调用尝试才写 `flight_request`；摘要请求也归自己的消息。观察点是 SDK 模型调用或原生传输，不是网络抓包，不能用行数反推内部鉴权、代理转发或 TCP 重连次数。尝试 ID 用现有 RequestEvidence 的关联号；前缀只取同会话、模型及运行时观察器算出的系统、工具、历史三段变化。不再序列化一遍正文，不从日志回填。基线没有可比前任；“观察到新压缩”与“历史改写”不是同一证据，二者都不能单独解释缓存失效。
- 两端展开时才读，未展开不轮询。`GET /session/:sessionID/flight-recorder` 每页默认 20、最多 50 行；游标绑定来源和会话，用 `(time_created, id)` 排序，同毫秒不漏行。只查当前分支的标识与统计，不拉整条消息或分片正文。已加载记录的汇总不代表会话总量；缺失、估算、零分母、读缓存超过总输入等情况不能冒充实报命中率。
- 新表每会话最多 128 次，随消息或会话删除。最终状态只能更新仍在的尝试，不能复活已淘汰的行。只记标识、状态、数值和几种变化分类；不记正文、账号、请求头、响应正文、路径或错误文本。采集失败不等于模型失败。

## 取舍

不把两种记录拼成一个计数：续写和重试让步骤与请求不能一一对应。没有实测的工具耗时、首字时间或服务端缓存原因就不画；“首事件”不是“首字”。没有单独服务、定时扫库或按流分片写盘。本功能不修改模型输入、工具描述、固定前缀或缓存键；新增模型上下文为 0 token。

旧步骤的部分索引以一次升级时扫描 `part` 换取查询不必全场排序。隔离 SQLite 样本（1,500 条消息、6,000 个分片、翻 21 行）中，`EXPLAIN QUERY PLAN` 从临时 B 树变为复合索引范围扫描；11 次热查的中位数从 3.067 ms 到 0.032 ms。这是合成读侧样本，不是现有用户库的迁移耗时或整端性能数据。

## FR-02 缓存诊断

请求详情保存同一会话、模型、运行时桶中上一次成功采集的请求 ID。观察失败保留原因且跳过基准更新。GUI 和 TUI 只用该 ID 对应的已加载请求显示基准命中率。`wire` 比较系统、历史和工具组成的有序序列，`serialized` 比较整份请求 JSON。压缩以本地标记推进或观察到的回执为证据，回执的 Token 数为估算值。

新增 `diagnostics` 版本为 1，旧行可继续读取。每行诊断是三个固定分段、一次基准关联、有限枚举、至多一组聚合压缩统计和一组供应商归因。每会话仍保留 128 条，压缩只聚合观察器已保有的至多 128 份待消费回执。同桶最多多保留一个请求 ID 与六个匿名亲和指纹，写入诊断仅取变化分类和数值。

模型输入、固定前缀、缓存键与出站顺序沿用既有路径。固定前缀增量为 **0 字节、0 Token**。供应商报出的 Instructions 读写保留显式零。本次请求总量和 Instructions 归因数据一致时，才从总未读缓存中扣减指令未读量。DeepSeek 的 miss 记为未读缓存，Anthropic 的总输入在三个组成项齐全时计算。
